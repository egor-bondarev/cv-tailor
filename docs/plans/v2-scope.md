## V0. Качество по прогону DevOps-вакансии (вакансия вне профиля) — сделано, проверено повторным прогоном

Прогон (DevOps, далёкая от опыта вакансия) прошёл честно: `confidence: low` → вопрос пользователю, 7 правок, 0 отброшено, verify OK; 22 запроса к модели против 32 в прогоне M4 (агент больше не читал `src/`). Находки:

1. **Атрибуция результата.** Факт типа `scope` «X-related failures fell from A to B» стал «Cut … from A to B» и «fixes that cut …» — ревьюер дважды `partial`. Третий случай за v1 (см. M4, прогон 6). → Правило промпта: факт `scope` описывает состояние, а не действие кандидата — не превращать в «I cut / reduced»; глагол действия только из фактов `achievement`/`built`.
2. **Связи между фактами.** «Monitoring … with metrics in S3 …» соединил два отдельных факта отношением, которого нет в фактах — `partial`. → Правило: при объединении фактов в одно предложение не добавлять причин, «with/using/by» между ними, если факты этого не говорят.
3. **Авто-исправление по ревьюеру.** Вердикты `partial`/`unsupported` сейчас только показываются. → Один дополнительный цикл: замечания ревьюера возвращаются в tailor как ошибки, исправленный план проходит валидаторы и повторное ревью; что не исправилось — в сводку как сейчас. Настраивается (`review_fix_rounds: 1`).
4. **Слишком дробные требования.** Правило «дробить составные» дало 18 must_have (`AWS SES`, `AWS SNS`, `AWS SQS` отдельно) и 7 пробелов. → Уточнить: дробить разные компетенции, а перечисление одного семейства («AWS: SES, SNS, SQS») — один пункт с подсписком; пробел внутри пункта показывать частично.
5. **Слабое совпадение.** Для вакансий вне профиля полезно предупреждение в сводке: доля покрытых must_have (например, «covered 6/18») и пометка, если меньше половины, — чтобы решать, стоит ли откликаться.

Проверка повторным прогоном той же вакансии: 10 must_have вместо 18 (семейства сгруппированы, недостающие элементы в `notes`); результат-факт остался результатом; связей между фактами не добавлено; ревьюер отметил одну правку `partial`, после одного раунда исправления все правки `supported`; в сводке «3/10 backed … weak match». Найдены и исправлены в SKILL.md: агент правил уже переименованный `output` на повторе и читал большие входы через `cat`.

## V1. Скриптовый режим `cvtailor run` — сделано в ветке `v1-scripted-run`

Как это выглядит для пользователя: ничего не меняется — в чате `/cv-tailor` с вакансией. Скилл запускает `cvtailor run`, Python сам вызывает модель на каждом ИИ-шаге (свежий маленький контекст на шаг), а чат-агент только передаёт вопросы и показывает сводку. Тот же `cvtailor run` можно запустить из терминала.


- `cvtailor run --company X [--url …] [--resume ID]` проходит весь прогон сам: на каждом шаге `ai` Python вызывает модель подпроцессом с промптом и входом шага, проверяет ответ и при ошибках повторяет (до `max_ai_retries`).
- Исполнитель ИИ-шагов настраивается в `config.yaml`: `ai_command` для каждого шага или общий (по умолчанию `claude -p --model <model>`), модель на шаг (`models: {extract: haiku, route: haiku, analyze: sonnet, tailor: opus}` — значения выберет V8).
- `ask_user`: `cvtailor run` останавливается с вопросом в JSON (как `next`); скилл задаёт его в чате и продолжает `cvtailor run --answer …`. Из терминала — вопрос через `input()`; `--resume` / `--non-interactive` — без вопроса (лидер ранжирования, пометка в сводке).
- Каждый вызов модели получает только промпт и вход шага: оценка ~50–60k токенов входа на прогон против ~3,5M в сессии Claude Code.
- Скилл `/cv-tailor` остаётся: в чате удобно отвечать на вопросы и смотреть сводку; он сможет звать `cvtailor run`.
- Журнал вызовов: модель, токены, время, попытки — в `runs/<run>/ai_calls.jsonl` (нужно для V8).

## V2. Обоснование правок комментариями в Google Docs — сделано в ветке `v2-doc-comments`

- После применения правок Python создаёт по комментарию на каждую операцию: причина, id и краткие формулировки фактов, вердикт ревьюера (`partial`/`unsupported` — с цитатой).
- Ограничение API: Drive API создаёт комментарии к Google Docs, но не умеет привязывать их к фрагменту текста — комментарий появится в панели комментариев без выделения. Поэтому текст комментария начинается с цитаты новой формулировки («op 3 · «Built an initial Playwright…» — …»), чтобы её было легко сопоставить с предложением. Проверить на живом документе, как это выглядит; если неудобно — ограничиться `review.md`.
- Комментарии удаляются или разрешаются пользователем как обычные; `final` их не проверяет.

## V3. Правка прошлых мест работы по приоритету — сделано в ветке `v3-past-roles`

- `editable_companies` в `resumes.yaml` становится упорядоченным: по умолчанию редактируемы два последних места работы с приоритетом 1, следующие — с приоритетом 2, 3, … (или явный список `{company: priority}`).
- Анализ и tailor видят приоритет блока; правило промпта — сначала правки в местах приоритета 1, в более старых — только при явной пользе для вакансии.
- Ограничения валидатора: не больше N операций на место приоритета ≥ 2 (по умолчанию 1), общий бюджет длины тот же.
- Факты прошлых ролей уже есть в `facts.json`, `role_map` уже умеет сопоставлять любые редактируемые роли.
- Проверить на вакансиях, где важен прошлый опыт (нагрузка, UI на Selenium, chaos-тесты).

## V4. Роль не разрывается между страницами — сделано в ветке `v4-keep-roles-together`

Итог: проверка в `cvtailor final`, когда предложений не осталось (до ревью вёрстка ещё не окончательная: пользователь может отклонить правки), исправление — прямой правкой по `final --fix-layout` после подтверждения пользователя. В реальных резюме разрыв задан стилем `pageBreakBefore` на заголовке компании, а не символом разрыва, поэтому переносится стиль (поддержан и символ `pageBreak`). Проверено на двух реальных копиях: 3 страницы со «висящими» буллетами → 2 страницы.

Проблема: после правок буллеты одной роли оказываются на двух страницах (заголовок роли и часть буллетов — внизу страницы, остальные — на следующей), а старый разрыв страницы, стоявший после последнего буллета этой роли, теперь создаёт пустоту.

- Определение разрывов: Docs API не отдаёт вёрстку — в `documents.get` нет страниц и положения строк, только явные разрывы страниц. Поэтому место разрыва видно только после рендеринга: экспорт копии в PDF через Drive API (рендер тот же, что в Docs) и сопоставление текста страниц с блоками (`parse` знает роли и их буллеты). Это автоматически, без участия пользователя.
- Исправление: вставить разрыв страницы (`insertPageBreak`) перед заголовком роли и удалить прежний ручной разрыв, если он стоял сразу после последнего буллета этой роли.
- Когда: после `final` (пользователь уже принял правки, вёрстка окончательная) — отдельным предложением или прямой правкой по подтверждению; либо в `verify`, если PDF-экспорт учитывает предложения — проверить при реализации.
- Тест на фикстуре с ручными разрывами + проверка на живом документе.

## V5. Вакансия по ссылке — сделано в ветке `v5-vacancy-url`

Итог: `init`/`run --url`; текст из schema.org `JobPosting`, иначе из `<main>` или видимого текста; компания только из `JobPosting` (иначе `--company`). Проверено на Greenhouse, Lever и сайте компании; extract на скачанном тексте отработал штатно. LinkedIn и страницы, требующие JS, отдают слишком мало текста — тогда текст передаётся через stdin.

- `cvtailor init --url <link>`; в скилле — «подгони под вакансию <ссылка>».
- Python скачивает страницу (только `http(s)`, таймаут, лимит размера, без cookies) и извлекает основной текст; сохраняет `vacancy.url`, `vacancy.html`, `vacancy.txt`. Компания и роль — со страницы, если не переданы.
- Если страница не отдаёт текст (нужен браузер или вход, как у LinkedIn) — действие для агента: прочитать страницу своим веб-инструментом и передать текст через stdin; в скриптовом режиме — попросить вставить текст.
- Текст страницы — источник для хука письма (V6): утверждения о компании проверяются как подстроки этого текста.

## V6. Сопроводительное письмо

### Решения пользователя

- Язык письма — язык вакансии.
- Пишется параллельно с работой над резюме (общий анализ вакансии и факты).
- Формат — простой текст без нечитаемых символов: копируется и вставляется без потери форматирования, экспортируется в любой формат. Результат — Google Doc рядом с копией резюме, имя `<Имя Фамилия>. Cover Letter - <Роль>`.
- Ревью вместе с резюме: пользователь смотрит предложения в резюме и текст письма, в чате говорит «ок» или что поправить; правки письма и повторные правки резюме идут тем же циклом. После «ок» — `final` (проверка резюме) и автоматический экспорт **резюме и письма** в PDF в папку компании.
- Объём — ограничение в символах (см. ниже); по запросу письмо урезается до переданного лимита (у некоторых сайтов есть лимит поля).
- Хук про компанию — опционален и берётся только из страницы по переданной ссылке; точное определение хука — совместный брейншторм перед реализацией (кандидаты: цель компании, её лозунг, описание проекта).

### Что взято из примеров (docs/private/cover-letter-examples.md)

Общие черты четырёх писем:
- обращение к компании или рекрутеру («Dear <Company>», «Dear <Company> Recruiter»);
- открытие: кто я и на какую роль подаюсь, плюс энтузиазм; в лучшем примере — цитата миссии компании, связанная с личной ценностью;
- тело: стаж и специализация, 1–2 конкретных проекта или стек;
- мотивация: почему эта позиция и компания;
- закрытие: благодарность, отсылка к резюме, приглашение связаться, подпись.
- Объём: короткие ~650–750 символов, средние ~950, длинные ~1300.

Чего в примерах избегать (видно по ним же): общие слова («thriving, innovative company»), непроверяемая бравада («whatever it takes»), отсылка «подробнее в CV» вместо конкретики, грамматические ошибки.

### Лимиты в символах (с пробелами, без шапки с контактами)

| Режим | Цель | Жёсткий максимум | Основа |
|---|---|---|---|
| `full` (по умолчанию) | 1300–1800 | 2000 | ≈ половина A4 при 11pt (~25 строк по ~80 символов) — по правилам Notion; длинный пример ~1300 |
| `short` (по просьбе урезать) | 650–900 | 1000 | короткие примеры ~650–950 |
| `--max-chars N` | ≤ N | N | лимит поля на сайте вакансии |

### Алгоритм для ИИ (сводка правил Notion и примеров)

**Подготовка (не пишется в письмо):**
1. Из вакансии — 3–5 ключевых требований и слов (must_have и главное из обязанностей).
2. Из анализа резюме и фактов — 2–3 самых сильных совпадения и 1–2 достижения с эффектом (числа — только из `metrics`).
3. Из страницы вакансии — найден ли хук (по определению после брейншторма); если нет — абзац о компании строится на её описании из той же страницы без оценок.
4. Мотивация — из двух источников: (а) постоянный раздел `motivation` в приватном `profile.yaml`, который пользователь пишет один раз (что ищет в работе, какие продукты и задачи интересны, ценности); (б) необязательный короткий ответ на вопрос «почему эта компания» в конкретном прогоне. Модель соединяет их с тем, что сказано о компании на странице вакансии; придумывать мотивацию нельзя — без (а) и (б) абзац строится только на совпадении вакансии и опыта, с пометкой в сводке.

**Структура письма (абзацы через пустую строку):**
1. Приветствие: по имени, если адресат известен; иначе «Dear <Company> team» / «Dear Hiring Team» (на языке вакансии).
2. Введение (2–3 предложения): роль, на которую подаюсь; хук про компанию, если есть, с мягкой формулировкой и привязкой к моему опыту или ценности; не пересказ резюме.
3. Ценность (3–5 предложений): совпадения с ключевыми требованиями словами вакансии; 1–2 достижения с эффектом; только факты, их глаголы и числа.
4. Почему эта позиция: мотивация, что могу дать именно этой команде.
5. Закрытие: благодарность за время, готовность обсудить, приглашение связаться.
6. Подпись: имя.

Шапка с контактами (имя, email, телефон, LinkedIn) подставляется Python из приватного `profile.yaml` и во внешние модели не уходит.

**Урезание (`short` или `--max-chars`):** убирать по порядку — второе достижение → детали мотивации → хук → третье совпадение; приветствие, одно совпадение с достижением и закрытие остаются всегда.

**Стиль:** первое лицо, конкретно, слова из вакансии естественно, без клише и превосходных степеней, без пересказа резюме.

### Где живут правила и как устроен скилл

- `prompts/cover_letter.md` (в репозитории): сводные правила из Notion и примеров, алгоритм, лимиты, обезличенные короткие образцы абзацев.
- `docs/private/cover-letter-examples.md` (вне git): очищенные исходные примеры — только справка для автора промпта, в модель не передаются.
- Один скилл `/cv-tailor`: письмо — ветка того же прогона (общие вакансия, анализ, факты, папка, harness). Отдельный вход `/cv-letter` — для «только письмо» по уже существующему прогону и для урезания до `--max-chars N`; он вызывает тот же `cvtailor`.

### Проверки

- Лимит символов режима.
- Утверждения о кандидате — со ссылками на проверенные факты (`evidence`), числа — по правилу чисел резюме.
- Утверждения о компании — с цитатой-источником, которая дословно есть в тексте страницы вакансии.
- Простой текст: прямые кавычки и апострофы, дефис вместо длинного тире, без маркеров списков, эмодзи, неразрывных пробелов и управляющих символов.
- Язык письма совпадает с языком вакансии.
- Ревьюер второй моделью: подтверждённость утверждений, нет пересказа резюме.

## V7. Запуск из других ИИ

- Агентские инструкции для Codex (`AGENTS.md`) и Gemini CLI (`GEMINI.md`): тот же цикл, что в `SKILL.md`, общий текст — один источник.
- Скриптовый режим (V1) с исполнителем `codex exec` или `gemini` для ИИ-шагов.
- Настройка — целиком у пользователя: кто выполняет ИИ-шаги (`ai: claude | codex | gemini`) и кто делает ревью (`review: {enabled, by: codex | claude | gemini | none}`). Единственная подсказка инструмента: если автор и ревьюер — одна и та же модель, в сводке пишется предупреждение (модель хуже замечает собственные ошибки); запускать это не мешает.
- Проверка: по одному прогону на каждом исполнителе.

## V8. Eval-набор и эксперименты по моделям Claude

Небольшой, но настоящий eval: заодно он становится регрессией для любых правок промптов (вместо ручной «заморозки»).

- **Набор вакансий** (локальные HTML/TXT, 12–20 шт.): ~1/3 точно по профилю, ~1/3 соседние роли (SDET, platform, DevOps, UI-автоматизация), ~1/3 далёкие (продакт, бэкенд-разработчик). Первые 10 уже есть — вакансии прогонов v1 в `runs/`.
- **Профили:** приватный — реальные резюме и факты пользователя (локально); публичный — вымышленный кандидат с тремя резюме и `facts.json` для репозитория (резюме из открытых источников не берём: персональные данные и лицензии).
- **Прогон без Google:** `cvtailor eval --set <dir> --models …` проходит extract → route → analyze → tailor → review на сохранённой копии документа (`copy.json`), без копирования и применения.
- **Автоматические метрики:** правильный выбор резюме (разметка набора), обнаруженные пробелы против эталонных, отброшенные валидаторами операции, повторы, вердикты ревьюера, длины, токены и время; для далёких вакансий — «не выдумал» (0 `unsupported`) и предупреждение о слабом совпадении.
- **LLM-судья** (опционально): релевантность правок вакансии по рубрике; калибруется на прогонах, которые пользователь уже ревьюировал.
- **Эксперимент по моделям:** матрица Opus / Sonnet / Haiku по шагам на этом наборе; итог — модели по шагам в `config.example.yaml`.
- Для маленького инструмента это не избыточно, если держать набор маленьким: основная ценность — ловить регрессии промптов без ручных прогонов.

## Прочее

- **README для чужих пользователей.** Пошаговая инструкция для человека, который клонирует репозиторий и хочет подгонять своё резюме: настройка Google, требования к оформлению резюме, сборка `facts.json` по промпту, первый прогон, типичные ошибки. Частично есть в README; не хватает сквозного руководства и проверки «с нуля» на чистой машине.
- **Технический долг** (отложенные мелочи из ревью M2 и M3) — по мере надобности:
  - `in_output` кэширует «нет доступа» для глубоких папок; переименование самой папки результатов разрешено;
  - повторный приём на ту же компанию и компании без `HEADING_3` молча нередактируемы (частично закрывается V3);
  - smart chips / rich links / сноски не учитываются; `norm_style` без `smallCaps`;
  - роль без intro, у которой удалили все буллеты, даёт ложную ошибку `final`;
  - ложные срабатывания чисел (`five-person`, `1,000` против `1000`);
  - отчёт показывает выбор резюме ИИ, а не ответ пользователя;
  - CLI: `StopIteration` при удалённом резюме, не ловится `YAMLError`, относительный `run_dir`;
  - сиротская копия при сбое между `copy_doc` и сохранением состояния.
